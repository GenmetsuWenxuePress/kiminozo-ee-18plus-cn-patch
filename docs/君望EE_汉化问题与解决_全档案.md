## 第一部分：逆向与容器类

### 1.1 decryptKey.bin：64KB 密钥机制与「密钥丢失事故」★★

**现象**：容器（FPD/egpack）全部是 XOR 加密的，没有密钥什么都读不了。

**机制**：
- 密钥 = 64KB 的 `decryptKey.bin`（来自社区工具集 FSNr_tools）；
- **索引区与每个数据条目各自从密钥偏移 0 开始**（不是全文件连续 XOR）；
- 校验密钥正确性的方法：64KB、首字节 `46 1f 3c 08 76 0f 12 8d`。

**事故（真实发生）**：工程中一次系统清理把 `scratch/fsnr/` 目录删掉了，**密钥丢失**，构建直接中断。恢复方法：从 GitHub `kurikomoe/FSNr_tools` 的 **`scripts/` 子目录**重新拉取（注意：默认分支路径可能变，我们试了 `main` 分支 404、`master` 分支成功）。

**教训**：**外部工具与密钥必须复制进项目工作区保管**（我们后来把它放进项目 `fsnr/` 并写进了文档要求）。另外任何「临时目录」都可能被清理——不要在那里放唯一副本。

### 1.2 EER 官方包条目解密偏移陷阱 ★

**现象**：EER 官方 `patch00m.bin` 里的条目，用「从密钥偏移 0 起 XOR」解密——**解密出来是乱码**。

**根因**：EER 官方打包时的条目**不是**从密钥偏移 0 起 XOR（与游戏本体/自建容器不同）——需要**暴力定位偏移**（遍历偏移尝试解密，用可解析性做判据）。

**教训**：拿到第三方容器时，先验证「偏移假设」再做批量操作；不同来源的容器打包习惯可能不同。

### 1.3 egpack 头 `0x08` 长度字段：不同步 = 引擎拒载 ★★

**现象**：改写文本后重建 egpack，游戏**直接拒载**（黑屏/不加载）。

**根因**：egpack 头部偏移 `0x08` 存的是**文件总长（小端 u32）**——改写文本改变了文件大小，但字段没更新。

**解法**：每次重建后 `struct.pack_into('<I', out, 8, len(out))`。

**教训**：格式里的「自述字段」（长度/计数/校验）在改写后必须**逐一同步**；把它写进重建函数本身（而不是指望调用方记得）。

### 1.4 ★★★ 幽灵 token：正则扫描器的缺陷与结构式解析器（本项目最隐蔽的坑）

**背景**：egpack 的 token 形式是 `\x87 + 4字节槽 + \xa6 + 值 + \x00`。最直觉的解析法 = 正则 `re.finditer(rb'\x87....\xa6')` 全局匹配。

**缺陷触发条件**：当**文本值内部**恰好含 `\x87....\xa6` 字节序列时（CJK UTF-8 字节流的自然巧合）。**真实案例**：中文「采**取妥**善措施的」= 字节 `E9 87 87 E5 8F 96 E5 A6 A5 ...`——其中 `87 E5 8F 96 E5 A6` 正好匹配 token 模式（「采」的末字节 + 「取」+ 「妥」的前两字节）！

**后果**（正则解析器）：
- 该匹配被当成**幽灵 token**：前一个 token 的值读取已经吞掉了这些字节（读到 `\x00` 为止），幽灵又被当独立 token 重发；
- **重建时文本片段被复制**（输出比输入多字节）；
- **不幂等**：`rebuild(rebuild(d))` 继续变长（实测 +18 ~ +484 字节/次）；
- token 计数虚高（实测污染包 109,902 vs 干净解析 109,901）。

**隐蔽性（为什么难发现）**：
- 引擎**容忍**多余 token——普通内容照常显示，游戏里看不出异常；
- 不做**逐字节检验**就发现不了；
- **「某文件过检」不可外推**——我们最初两个测试文件恰好不含幽灵模式，误以为解析器没问题。

**发现过程**：字节级复核时发现「解析→重建逐字节一致」不成立 → 逐文件排查 → 定位到含幽灵模式的文件 → 分析出机制。

**出厂包的实际状态（诚实披露）**：交付 v20 容器里**存在 41 个幽灵 token**（涉及 25 个文件，theater 8 个最多）——它们是早期用正则版构建时留下的。**良性**：值完好、引擎忽略、实机全通过（用户全程试玩确认）。但它们确实是脏数据，文件也因此略微膨胀。

**正确解法 = 结构式位置驱动解析器**（详见指南 §4.5）：
- 位置驱动、逐段消费：每字节恰好消费一次并原样保留；
- 文本值内的幽灵序列被当作值的一部分吞掉，不会重发；
- **双检验门槛**（出货强制）：
  1. 往返逐字节：`eg_build_struct(d, *eg_parse_struct(d)) == d`（对未修改文件）；
  2. 幂等：同一输入重建两次输出相同；
  3. 修改重建后，与原始文件 diff **只落在预期槽位**。

> ⚠️ 一个反直觉的点：「往返逐字节一致」对结构式解析器**是构造性成立的**（每个字节都被原样搬回）——它不能证明解析边界正确；**真正有判别力的是「幂等性」与「记录级语义比对」**（token 流对齐后检查差异是否只在预期槽位）。我们最终就是靠「token 流对齐 + 语义比对」确认出厂包除幽灵外无其他损伤。

**教训**：
1. 用**位置驱动**解析器，不用全局正则；
2. 出货门槛加「幂等 + 语义 diff」双检验；
3. 「测试通过」不等于「没问题」——**单变量扩样**（多测几个文件、专门构造含幽灵的样本）。

### 1.5 大容器重建的性能与内存问题 → 外科手术式重建 ★

**现象**：全量重建 60MB+ 的容器（每次修复都重建全部条目）耗时长、内存高；且修复只涉及少数文件。

**解法（外科手术式重建）**：
- 计算修复集合 → 通过 `units.jsonl` 的 `refs` 映射到**受影响的 egpack**；
- **只重建受影响的文件**；其余条目保留 `stored` 字节**原样搬运**（零改动）；
- 实测：705 条修复 → 只触及 93 个文件 → 934 条记录替换 → 回读 934/934。

**教训**：容器构建做成「增量式」——按需重建 + 原样搬运，天然保证「未触及条目字节不变」（还顺带成为验收项）。

### 1.6 FPD 字符串表 16 字节对齐：错一个字节 = 黑屏 ★★

**现象**：自建容器装机后游戏**黑屏**（不崩溃、无报错，就是黑）。

**根因**：官方容器的**字符串表尾部按 16 字节对齐**（用 `\x00` 补齐）——引擎校验/依赖该对齐；我们最初没补。

**解法**：`strtab += b'\x00' * ((-len(strtab)) % 16)`。

**教训**：官方容器的「无意义填充」可能是有意义的——**重建时保持一切字节级惯例**（对齐、填充、字段值），别自作聪明"优化"。

### 1.7 `build_fpd` 的 `stored` 键陷阱：修改静默失效 ★★

**现象**：替换了条目内容、重新构建容器——装机后**什么都没变**；回读检查竟然还"通过"。

**根因**：`build_fpd` 优先使用条目自带的 `stored`（存储字节）——如果替换内容时只改了 `plain` 而没 `pop('stored')`，**新内容被忽略，旧字节原样写回**。

**解法**：替换条目内容时**必须** `e['plain'] = 新内容; e.pop('stored', None)`。

**教训**：「静默失效」是最危险的失败模式——**修改后一定要有能证明修改生效的检查**（回读断言具体内容，而不是只看文件大小/存在性）。

### 1.8 字节级对拍纪律（曾发现 1 字节级差异）★

**做法**：任何重建产物都与原版（或上一版）做**逐字节对拍**：
- 未修改的条目：sha256 必须一致；
- 修改的条目：diff 范围必须**精确落在预期位置**；
- 整体：记录 size/sha256 进版本链（见指南附录 B.2）。

**实例**：工程中靠它发现过重建产物与原版**差 1 字节**级别的差异（长度字段/填充边界类问题）——肉眼与功能测试都发现不了的差异，只有对拍能抓。

### 1.9 「TEXT ID NOT FOUND」与 theater 超大包收敛 ★

**现象**：回想画廊（theater）相关场景报 `TEXT ID NOT FOUND`；仅**包尾部记录**失败。

**收敛过程**（数据层全绿后转结构层）：
1. 数据内容逐槽比对（槽序/分隔符/空槽/跨包 ID 碰撞/语音命中）——全绿；
2. **重建污染检验**（§1.4）——出厂包可能带幽灵字节；
3. 失败区间**字节偏移实测**——定位失败记录在包内的绝对偏移；
4. 包尺寸/截断假说——实测异常包 = 全容器唯一 >2MB 者（第二大仅 0.51MB）。

**引擎侧已核实事实**（排障时避免瞎猜）：
- 文本管理 = 全局单 `unordered_map`（FNV-1a）+ 纯 ID 键，**无「包」概念**；未命中 → `TEXT ID NOT FOUND`；命中但槽空 → `NOT TRANSLATED`；
- 加载器按 `id` + `jp` 键读记录；每 ID 仅 2 槽（jp/en）；重复 ID 仅打日志跳过（无害）；
- 读函数在 `erc_nospfx.dll`（导出名混淆为 `eg<hash>`）。

**纪律**：数据层逐槽比对全绿后，**勿再纠缠数据内容**，转引擎/加载/结构层排查。

### 1.10 超大包瘦身（theater 专用）★

**背景**：theater.egpack 是全容器唯一 >2MB 的剧本包（2,165,455 B）。

**瘦身原理**：每条记录有 8 个**空语言槽**（各 7B）——引擎只读 id/jp/en 槽，空槽可删：
- 8 空槽 × 7B × 9991 条 ≈ 546KB 可省；
- **删槽实现注意**：丢弃空槽 token 时**只保留其 gap**（记录首槽 gap = `\x85\xdb` 分隔符，不可连带删除）。

**实测**：原始 2,165,455B → 清创 2,239,843B → 清创+瘦身 1,680,347B（出厂 v20 的 theater ≈ 1,681,327B）。

**验收**：单变量真机验证（装进游戏跑回想场景）。

## 第二部分：翻译类

### 2.1 控制符被吞/增删 → 质检 + 修复回路（85% → 100%）★★

**现象**：AI 译文里 `\w`（停顿）和 `\n`（换行）**偶发丢失/合并/新增**——控制符错乱会导致游戏内文本显示/翻页异常。

**解法（三层防御）**：
1. **质检分离**：**硬码**（`\p \n \k \f`——数量与顺序必须完全一致）vs **软码**（`\w`——数量尽量一致，位置可就近调整，容忍）；
2. **每条即时质检**：翻译引擎对每条结果算 `ok`（硬码合规）/`soft_ok`（全码合规），不合规的自动进修复队列；
3. **修复回路**（`fix_codes.py`）：把「原文控制符清单」附在输入里重译（提示词强化：「数量一致、顺序一致、种类一致」），修复率 13/15，余量手工 → **100%**。

**实测**：主通道首过硬码合规率 ≈85%；成人集 100% 干净；普通集终验 75,379 条全查 **0 不一致**。

**教训**：对「格式性约束」不要指望模型一次做对——**把质检写进管线**（每条立即验），把修复做成**专用通道**（带清单重译）。

### 2.2 批量级拦截：一条敏感行毁掉整批 ★★

**现象**：翻译批次偶发整批失败（`KeyError:'candidates'`——API 返回被拦截）；成人集实测 40 条这种。

**根因**：批次里只要有一条内容触发 API 拦截，**整批响应都拿不到**。

**解法**：失败重试必须**降到 `--batch 1` 逐条重试**（单条时拦截只影响该条，其余正常）；仍被拦截的少量条目改走本地模型兜底（无审查）。

**教训**：批量 API 的失败模式是「整批连坐」——**重试策略要能降粒度**。

### 2.3 真实换行 vs `\n` 转义 ★

**现象**：模型偶发输出**真实换行字节（0x0A）**而不是两字符转义 `\n`——游戏内显示异常。

**解法**：`fix_ws.py` **确定性归一化**（不调 API）：
- 真实换行 → 转为 `\n` 转义（仅当该条 JP 的 `\n` 数还有余量）；
- 超出余量的多余换行 → 删除（并计数报告）；
- `\t` → 删除；`\r` → 并入换行处理；
- 修复后重算 ok/soft_ok。

**教训**：「模型输出格式的偶发偏离」用**确定性脚本**修，别浪费 API 重跑。

### 2.4 日文残留 / 繁体残留清零 ★

**现象**：终态扫描发现残留：促音 46 + 「穂村」2 + 注释记录 9 + 缺 `\n` 1 + 小假名 1。

**解法**：全库正则扫描（假名区 + 常见日文/繁体字形清单）→ 逐类清零 → **全库零假名/零繁体残留**（扫描代码见指南 §7.7）。

**教训**：术语表管不住「偶发残留」——**终态必须有全库字形扫描**（把「零残留」作为出货门槛之一）。

### 2.5 术语不统一 → 「称谓政策」（用户拍板）★★

**现象**：复检发现大量称谓/术语不一致：如「孝之」有 君/先生/哥/裸名 四种叫法（1,740 条涉及）；「星乃」有 小姐/女士/同学（240 条）等。

**用户拍板（原文精神）**：
> **称谓本身随场景/情境变化，不能一概而论** → 称谓类**不做全局统一**；全局扫描降级为「发现可疑偏差」辅助工具，修复仅针对**复检判定为错误**的条目（逐条）。

**已拍板固定的术语**（全局统一）：餐厅名=**天空神殿**；文绪昵称=**文绪酱**；绘本名=**玛雅乌尔**；大川→**天川**（人名错字）；肥兽→**胖兽**。

**教训**：全局统一要有**明确的适用边界**——人名固定词可以全局替换；**称谓（依赖语境）不能一刀切**，否则会制造新错误。

**规模**：复检 26,700/75,379 条（35.4%），69 个复检块（deepseek 子代理）+ Claude 试跑 807 条（9 条发现，已并入）。

| 称谓/术语偏差 | 116+ | **高（全局扫描）** |

**关键方法（复用价值高）**：
1. **建议译文的外壳补全**：审校建议常缺 `「」` 和结尾 `\p`——候选顺序尝试（`「`+建议+`」`+尾部控制符 → 裸建议+尾部控制符），**只在硬码匹配时采纳，其余留人工，绝不猜**；
2. **内容锚点找回 key**：发现报告的 key 错位/损坏时，用报告里的特征子串（日文片段或中文文本）在语料里搜索定位真实 key——**全部找回了**；
3. **严重度优先去重**：同一 key 多次命中 → 只留最高严重度。

**诚实边界**：语义级问题（错译判断/上下文连贯）**无法脚本化**——未复检的 65% 如需完整覆盖需续跑复检管线（脚本与批次就绪）。我们出货时接受了 35.4% 覆盖 + 全量结构性扫描。

### 2.7 ★★ 修复批劣化事故：EZ 层整体回滚 494 条（DLC 侧，最重要教训）

**前提判定**：DLC 官方 `en` 槽是**改编版**（非直译）——证据（3 例）：
- 「ぶっとばすわよ」（揍飞你）→ EN "I will slice off your tongue!"
- 「ふざけるんじゃないわよ」（别闹了）→ EN "...SHOVE IT UP YOUR ASS!"
- 「さっさと隠居すればいい」（该退休了）→ EN "How many years before the old geezer hit retirement age?"

**事故**：基于 en 差异自动生成的修复批（28 批 / 558 工单）应用了 494 条。抽查 12 条发现**系统性劣化**：
- 8/12 **丢开括号**「」（apply 器只验控制符，括号损坏漏网）；
- 词句破坏：莫名地恐怖 → 无性地恐怖；
- **跟随英译改错**：兽人看穿一切 → "别担心，我了如指掌她的每一步"。

**处置**：**整体回滚**（恢复 prev4_zh，494 条）→ 改为「**JP 权威重判**」模式（修复提示词明示「英译是改编、以日文为准、无误则原样输出」）→ 修复员 no-op 输出验证该模式（44 条维持原译 ✓）。

**沉淀规则（铁律）**：
1. **任何自动修复批先抽样评审再应用**；
2. apply 器加**括号配对校验**（「」数量 + 顺序）；
3. **版本链字段**（prevN_zh）是回滚的前提，**apply 前必写**；
4. 手动修复放自动链**之后**（实测被 round2 覆盖过 1 例）。

### 2.8 串位（mis-assignment）：译文张冠李戴 ★

**机制**：翻译批次输出串行——item N 拿到邻近行的重译（用词变体可辨：砰/咚、哈鲁卡/遥）。

**检测扫描**（按性价比）：
```python
# ① \w 数量差 ≥2（正常 0-1）
d = len(SOFT.findall(jp)) - len(SOFT.findall(zh))
# ② zh 重复组（同译文出现在多 key）
# ③ 极端改写比：len(zh)/len(jp) > 3×
# ④ en-zh 对照层交叉
```
**修复**：手动重译 + `\w` 逐位对齐（5/5、6/6 对齐），用相邻行 prev/next + en 槽佐证。

**教训**：批量翻译的**位置错位**是真实故障模式——出货前必须跑串位扫描。

### 2.9 词汇误读：jp 单参照会漏检 ★

**案例**：「ちんちくりん」（小矮子）被本地模型误读为「肉棒」（ちんちん 联想）——**jp 审校没报**，en-zh 对照层抓出来的。

**对策**：低质通道段（本地模型兜底的部分）做 **jp+en 双参照**定向复扫（en 虽是改编，但足以暴露"意思完全不同"的误读）。实测：850 条 → 9 批 → 48 工单 → 全部应用。

**教训**：单一参照有盲区——**jp 判"准不准"，en 判"对不对"**，两层都要有。

### 2.10 批量静默失败与假警报 ★

**静默失败模式**：agy 通道 `eligibility check failed` / `oauth2/userinfo: EOF` → 输出只有 90-250 字节（实际是错误信息被当"结果"保存）。**检出后清空重跑（降并发）**。

**假警报**：`dlc_034`「29B」输出被疑为失败——实际是**零问题批的正常输出**（"共检100条，问题0条"）。**小输出不一定是失败，先看内容**。

**教训**：批量任务的「成功/失败」判定要看**内容模式**，不能只看大小/退出码；重跑前先确认文件内容。

### 2.11 翻译单元库的工程细节 ★

- 单元键 = `sha1(jp)[:12]`——**重复台词全游戏只翻一次**（去重 30.7%）；
- `refs` 字段（`{文件idx}-{记录序}`）是回写/修复/外科手术的**定位基础**——务必保留；
- 语料里存的 `en` 槽值**可能自带错**（官方改编/错误）——只作参考，**翻译以 jp 为准**（提示词里已明示）。

## 第三部分：字体渲染类 —— 「方框」攻坚全程（★★★ 本项目最大难点）

> 这一部分是整个工程投入最多、弯路最多的地方。**如果你只读一节，读这一节。**

### 3.1 症状全记录（先完整感受一下这个问题有多迷）

1. **对话正常，backlog（历史回顾）方框**：同样的字（如「濑」）在对话框里渲染正常，在 backlog 里是方框「□」；
2. **同一 backlog 里逐条不同**：H 场景条目方框、普通条目正常——**同一条文本流里两种表现**；
3. **名字框方框**（部分时期）；
4. **字集特征**：方框字集与「原版日文字体的缺失集」**逐字全等**（这是关键线索！）。

**先记住这条反推法**：**哪个 UI 元素坏 = 哪个字体槽被拒**（槽位↔元素映射表见指南 §9.1）。

### 3.2 排查路线全图（假设 → 实验 → 结论）

| # | 假设 | 实验 | 结论 |
|---|---|---|---|
| 1 | 字体被 patch00d/01m 遮蔽 | 检查两容器：4933 条/0 字体、4 条/0 字体 | ❌ 证伪（字体只在 pack.bin 原版 7 条 + 我们的容器里） |
| 2 | 引擎忽略补丁容器字体 | 对话中文正常 = Message 槽替换生效 | ❌ 证伪（补丁字体确实被加载） |
| 3 | mimic 字形损坏 | PIL 渲染全部完好；字形级检查（BoundsPen）零异常；cmap 全覆盖 | ❌ 证伪（字形没问题） |
| 4 | name 表没移植 | name 表 36 条记录移植完整（nameID 1/2/4/6 全对） | ❌ 证伪（验收不看 name 表！） |
| 5 | 剧本/XML 里有字体样式节点 | base XML = 内联 JP 文本、localized XML = `$game_tXXXXX` 引用；两版 message 节点均只有 cut/line/text/speaker/voice/wait | ❌ 证伪（字体解析完全在引擎侧 CFG） |
| 6 | 只唯一化 fontNames 就算修复 | 实测名字框仍方框 | ❌ 证伪（不够） |
| 7 | 容器内身份全唯一即足够 | 全唯一但未对齐原版的版本实测仍被拒 | ❌ 证伪（唯一化不充分） |
| 8 | **fsSelection 类别必须与原版一致** | 身份对齐但 fsSel 为粗体类 → Common 槽被拒（backlog 方框）；类别相符后改善 | ✅ **根因之一**（见 3.4） |
| 9 | **字体条目数过多污染字体池** | 单变量：v18（5 字体）✗ → v19（2 字体）✓ → v20（3 字体）✓ | ✅ **最终根因**（见 3.5） |

> 注意 #8 与 #9 是**两个不同层面的问题**，在不同阶段各自成立过；最终出厂验证的是 #9 的方案（配合 #8 的类别对齐）。第 8 条的证据：同一字体、类别不同 → 被拒/通过的分界非常清晰。

### 3.3 关键取证方法（这套方法论值得学）

**① 缺失集反查（定位「实际渲染的是哪个字体」）**：
1. 取方框截图的**完整文本**（按译文库 refs 找源记录——⚠️ **refs 编号 = 语料清单 idx，不是剧本文件名的数字前缀**！实测 refs `003` = `10プロローグ_7月03日（金）`，而文件名 `003_1979年6月中旬～` 是另一条——先查 manifest 映射再搜文件，否则白找）；
2. 对截图全文的字符集，**逐候选字体算 cmap 缺失集**（**按子表分别算**，不只看并集——引擎实际用某一子表如 (0,3)/(3,1)）；
3. **缺失集与方框字集逐字完全相等者 = 实际渲染的字体** → 据此确定被拒的槽。
   - 实测：原版 beatfont1 的 (0,3) 子表缺失集与截图方框字集 **10/10 全中** → 锁定 Common 槽。

**② 截图判读纪律**：视觉模型全图扫描会「模式补全」——关键行**裁剪 + 2× 放大**后再逐字核对；**显式列出待查字（应正常与应方框两组都列）**，正反例都确认才采信。

**③ 装机历史重建**：`obb/patch00m.bin.bak_<日期>_v<版本>`（备份名 = 被替换版本）+ staging `patch00m.bin.v<N>.bin`（mtime = 构建时刻）→ 还原各版本状态、定位「何时引入」。

**④ 字体侧工具链**：
- 容器内字体清单（仅索引读取器——FPD 索引在前 ~1.8MB，数据区截断的头部切片也能解析）；
- CFF 身份四元组对拍（`fontNames[0]` / `FullName` / `FamilyName` / `Weight`）；
- fsSel 类别对拍（位判 `0x20`/`0x40`）；
- PIL 渲染验证（有映射 ≠ 字形非空）；
- 字形级检查（BoundsPen：`bounds=None` → 空字形）。

**⑤ 游戏日志捕获**：release 版引擎的 info 级日志（"create font … done"）不输出，只捕获到错误级 → 自研 **DBWIN 捕获器**（`_dbgcap.ps1`）+ 任务计划运行（DbgView 被系统拒 0x800710E0）。

### 3.4 根因之一：fsSelection 类别（静默校验）★★

**规则**：补丁字体的 `OS/2.fsSelection` **粗体位类别**必须与原版槽位字体一致——偏离 = **静默拒绝** = 回退原版日文字体 = 方框。

| 状态 | 身份对齐 | fsSel 类别 | 观测 |
|---|---|---|---|
| 身份对齐但 fsSel 为粗体类 | ✓ | ✗ | Common 槽被拒（backlog 方框） |
| 类别相符但身份为 Noto 名 | ✗ | ✓ | 曾观测被拒（见 3.6 的诚实边界） |
| **出厂版** | （保持 Noto 名） | **✓ 对齐** | **实机全通过** |

**各槽原版类别与出厂值**：

| 槽位字体 | 原版类别 | 出厂 mimic 实测 |
|---|---|---|
| UDKakugo（Message/Hud） | `0x0020`（粗体类） | `0x0020` ✓ |
| beatfont1（Common） | `0x0040`（常规类） | `0x0040` ✓ |
| Skip（Speaker） | `0x0000` | 按原版对齐 |
| BIZ（StaffCN） | `0x0040` | `0x0040` ✓ |

**回退链（为什么方框只出现在某些元素）**：
- 补丁字体被拒 → 回退到**同名文件的下一个来源**：
  - 主游戏：补丁层 + 资产层各一份（patch00m + pack.bin）→ 回退到**未替换的日文原版** → **方框可见**；
  - DLC：字体只在资产层一份 → 回退 = 同一已替换文件 → **无感知**。

**修复后自查（必做）**：① 容器内全部字体四元组两两比对；② 逐槽断言 fsSel 类别 == 原版；③ 重建容器替换条目（**先 pop `stored`**，否则静默无效——见 §1.7）。

### 3.5 根因之二（最终根因）：字体条目数污染字体池 ★★★

**转折点**：按用户要求「**从零开始分析，避免过去的操作影响判断**」——放弃所有旧假设，做**单变量实验**（一次只变一个东西）：

| 版本 | 字体条目 | 实验目的 | 结果 |
|---|---|---|---|
| v18 | 5 个（UDKakugo/beatfont1/Skip/LINESeed/BIZ） | 现状 | ✗ backlog 方框 |
| v19 | **2 个**（v5 的确切字节：UDKakugo + beatfont1） | 只减字体数 | **✓ 方框消失** |
| v20 | **3 个**（v19 + BIZ 加回——staff roll 需要） | 加回一个 | **✓ 方框仍消失** |

**结论**：容器内**字体条目数过多 → 污染引擎字体池**——这是 backlog 方框的最终根因。5 个就坏、2-3 个就好。

**出厂配置（v20，实测值）**：
- `FOT-UDKakugo_LargePro-DB.otf`（6,691,292 B）← CN-mimic（NotoSansSC-Bold 字形集；CFF `NotoSansSC-Bold` / fsSel `0x0020`）；
- `beatfont1.otf`（6,527,888 B）← beatfont1-mimic（NotoSansSC-Regular；fsSel `0x0040`）；
- `BIZ-UDMinchoM.ttc`（6,529,260 B）← BIZ-mimic（CFF `BIZUDMinchoM`；fsSel `0x0040`）；
- 全部字体 cmap ≈ 21,765 字形，测试字集零缺字。

**验证**：v20 容器与原版全量 diff —— 4,328/4,964 记录一致，全部差异均为预期汉化；装机实机试玩（对话/backlog/名字框/staff roll）全部无方框。

### 3.6 诚实边界（写给细心的复现者）

- 调试中期归纳过「**CFF 身份四字段必须对齐原版**」的假设，并有独立失败样本支撑（「身份对齐但 fsSel 错」的版本被拒）；但**最终出厂版并未对齐名称字段**（出厂值 = `NotoSansSC-Bold`/`NotoSansSC-Regular`/`BIZUDMinchoM`），且实机全通过。**即：以出厂实测为准——「类别对齐 + 条目数控制」是被验证的必要条件；名称字段的对齐故事作为调试史料保留，不要被它带偏。**
- 「双满足（身份+类别）⇒ 必过」在工程记录里**没有完成最终实机验收**（当时标记为"构建就绪"）；最终通过的版本是出厂三字体方案。
- **给复现者的操作顺序**：遇到方框 → ①先查 fsSel 类别对齐 → ②再数字体条目数（3 个起步）→ ③仍不行再看身份字段。每一步用单变量装机验证。

### 3.7 方框诊断树（速查）

```
方框出现
├─ 只在 backlog？
│   ├─ H 场景条目方框、普通条目正常 → Common 槽被拒 → 查 beatfont1（fsSel/条目数）
│   └─ 全部条目方框 → Common 槽整体回退 → 同上
├─ 对话正文方框 → Message 槽 → 查 UDKakugo 字体

├─ staff roll 方框 → StaffCN 槽 → 查 BIZ 字体
└─ 检查顺序（每个槽）：
    ① 该字体是否真的进了容器？（回读字体清单）
    ② fsSel 类别 == 原版？ 
    ③ 字体条目总数 ≤ 3？
    ④ 回退链下一层是不是日文原版？（pack.bin 同名文件哈希）
    ⑤ 缺字集反查（§3.3①）确认实际渲染字体
```

## 第四部分：构建与工程纪律

### 4.1 备份与版本链纪律 ★★

- **一切改动前先备份**：`<文件>.bak_<日期>_<版本>`（如 `patch00m.bin.bak_20260927_v12`）；
- **每一版容器记录**：size + sha256 + 构建脚本 + 关键参数（出厂版本链见指南附录 B.2）；
- **回滚 = 复制备份回去**——保留每一版备份就能回退到任意版本；
- 译文文件同理：`normal.jsonl.bak_20260927_112003`（修复前）→ 出事故（§2.7）时靠它回滚。

### 4.2 单变量原则 ★★

- 一次只变**一个**东西（如 v19：只改字体数，其余全部保持 v18 不变）；
- 效果 = 清晰的因果证据；混着改 = 事后无法归因（我们为此浪费过大量时间）；
- 对照实验要**从零重建判断**（用户原话：「从零开始分析，避免过去的操作影响你的判断」）。

### 4.3 防劣化协议（修复层应用前必过）★★

1. **任何批量应用前必须抽样评审**（EZ 事故的教训，§2.7）；
2. **分层应用、单一变量**：逐条修复层与全局扫描层分开应用，各自留哈希与回滚点；
3. **应用后复检抽样**：每层应用后抽 50-100 条人工核对；
4. **回滚方案先行**：应用前备份 + 哈希记录。

### 4.4 应用校验（dry-run 后再写）★

- 硬码全量校验（每条 `\p \n \k \f` 与原文一致），改动的每一行都验，写入后**全文件复验**（期望 0 不一致）；
- 建议译文**外壳补全**（§2.6），只在硬码匹配时采纳；
- 空建议、与单元不对应的建议 → 跳过（评审行错位）。

## 第五部分：装机与测试类

### 5.1 装机事故：把测试补丁装到了「真实游戏」上 ★★

**事故**：一次自动化测试假定「目标文件已是某版本」（想测「跳过已装」逻辑），但实际**目标游戏是干净未装的**——结果**真的把测试补丁装进了真实游戏**。

**教训（已沉淀为技能提示）**：
> **「预期跳过」类测试，必须先核验前置状态**——脚本要先断言环境（文件存在 + 哈希匹配），不满足就中止，绝不带假设开跑。

**修复**：测试全部改到**沙盒目录**（复制一份假的游戏目录结构跑安装/卸载流程），真实游戏只做最终验收。

### 5.2 游戏运行中的文件占用 ★

**现象**：替换目标文件失败（进程占用）；换名重试也时好时坏。

**解法**：装机前检查游戏进程（按 `kiminozs`/`kiminoaz` 前缀匹配进程名）；替换用 **while-locked 重试**（等锁释放，超时报告）；交付 exe 的自我更新也遇到过（`_swap_exe.ps1` 重试成功）。

### 5.3 Ending list 点不动 —— 游戏原始设计（不是汉化问题）★

**现象**：Ending 列表项无法点击/不显示。

**排查**：反复确认非汉化引起 → 最终确认**原作设计**：Ending list 读取**存档里的通关标记**，没通关就是空的——**原版游戏同样如此**。

**教训**：玩家报告的「bug」先分清「原作设计」与「补丁引入」——用原版对照实验。

### 5.4 回想画廊 8-4/8-5 是同一场景？—— 原作 A/B 版本 ★

**现象**：EER 回想画廊最后两格 8-4/8-5 看起来像「同一个 H 场景」。

**取证结论**：**原作设计 = 同一场景的 A/B 两版**：
- theater.xml 节点逐字节 = 原始（sha 相同）；
- 文本 71/227 条逐字相同、其余为改写变体；
- 8-4 段含口交序列（51 个 bg 引用）；8-5 段无（33 个）；
- **首句即有细微差别**（8-4「我用『公主抱』的姿势抱起爱美」vs 8-5「我以『公主抱』的姿势把爱美抱」）。

**教训**：翻译/质检时不要「修复」这种差异——它们是原作内容。

### 5.5 存档加密 → 改走「游戏自身 flag 机制」（解锁模块）★

**背景**：想实现回想/画廊全解锁。存档 = **压缩+加密流**（逆向成本高）。

**解法（绕开存档）**：解锁状态由游戏自己的 `<value_save>` **flag 机制**控制——扫描全部 XML 收集 67 种标志（回想 open_key 40 + 结局 + 章节），注入到每个剧情脚本（scr/*.xml，407 个）的根节点入口 → **任意场景加载即全解锁**。40 个回想 open_key 与存档标志 **40/40 对应**（验证机制理解正确）。

**教训**：正面硬刚（逆向加密存档）成本高时，找**系统自带的合法机制**（游戏自己的 flag 系统）达成同等效果。

### 5.6 装机验收纪律（重复强调）★★

- 装机 = 备份 + 覆盖 + **哈希校验**（脚本自带）；
- **验收由真人在真机做**（我们的惯例：交付文件 + 一键脚本 + 诊断工具，用户自己跑）；
- 报告诚实：**未过用户实机验收前，不宣称「成功」**。

## 第六部分：安装器类（单文件 C# exe）

> 交付形态从「脚本包」演进到「单文件安装器」的过程与全部坑。如果你也要做安装器，这一节是现成的排坑清单。

### 6.1 技术路线：PowerShell 脚本 → 原生 C# 单文件 exe

**为什么换**：脚本包对最终用户门槛高（解压/执行策略/依赖）；单文件 exe = 双击即用、零依赖（.NET Framework 是 Win10/11 自带）。

**技术方案**：
- C# 原生 exe（`csc.exe` 编译，.NET Framework 4.x）；
- **载荷尾部附着**：把全部补丁文件（约 1.1GB）以自定义格式**追加在 exe 尾部**；运行时**流式读取自身**解出载荷——零临时解压、零额外磁盘占用；
- 界面 = WPF（`ui.xaml` 编译为资源）；图标 = `/win32icon:app.ico`；界面头部 logo = 嵌入资源（`Assembly.GetManifestResourceStream` 加载）；
- CLI 模式保留（`-Cli [-InstallAll|-Uninstall|-Eer -Cn -Dlc]`）供自动化测试。

**载荷尺寸链（供参考）**：原生 exe 62,976 → +载荷 1,099,635,678 → +图标 1,100,055,519 → +头部 logo 1,100,174,303 → +版本信息 1,100,175,839 → +GUI 卸载代码 **1,100,177,375**（出厂）。

### 6.2 属性里版本号是 0.0.0 ★★

**现象**：exe 属性对话框显示版本 0.0.0。

**根因**：**csc 默认不写 VERSIONINFO，且会预嵌一个「空的 RT_VERSION 资源（中性语言 0）」**——我们后来写入的版本资源（0x0409）被那个空资源**盖住**。

**解法**：注入版本信息时**同时写两个语言槽**：`0x0409` + 中性 `0`（`UpdateResource(RT_VERSION=16, id=1, lang)`）——`make_version.py` 生成 804 字节 VS_VERSIONINFO，双槽写入后属性正常显示 `1.0.0.0`。

**教训**：Windows 资源系统的「预嵌空资源」会遮蔽后写资源——**多语言槽都要处理**。

### 6.3 图标「不更新」的真正根因：Windows 图标缓存 ★★

**现象**：换了 exe 图标，文件资源管理器**刷新也还是老图标**（用户两次反馈）。

**排查**：从交付 exe 内提取图标（多尺寸 16/32/48/64/128/256）→ **图标本身完全正确**（与源 .ico 逐字节/哈希一致）；问题不在 exe。

**根因**：**Windows 图标缓存数据库**（iconcache/thumbcache）——系统按缓存显示旧图标。

**解法**：清理 30 个 iconcache/thumbcache DB 文件 + 重启资源管理器。

**教训**：「图标没换」先验证 exe 内资源，再查系统缓存；**用户看到的 ≠ 文件里的**。

### 6.4 已装检测语义：哈希白名单 ★

**设计**：检测每一项的状态时——
- 目标文件 **sha256 == 我们的文件** → 绿「已安装」；
- 其余一切（原版/残留/未知）→ 灰「未安装」+ 提示「· 安装时将自动备份现有文件」；
- 安装行为不变（自动备份 + 安全覆盖）。

**坑（DLC 版）**：全新安装的 DLC 自带**原版**文件，早期逻辑把它判成「**已安装其他版本**」——误导用户（用户原话反馈："显示DLC已安装其他版本，但是又不影响安装"）。**修复**：改为灰「未安装（当前为原文版）」+ 备份提示。

**教训**：检测的**语义**要面向用户写清楚——「不是我们的文件」≠「已安装其他版本」。

### 6.5 已装组件重复安装 ★

**现象**：三项都显示已安装，点「安装」**又装了一遍**（用户实测报告）。

**解法**：安装前做**哈希级检测**——已装的组件自动跳过（日志「已跳过（已安装，无需重复安装）」）；全部已装时完成页显示「✓ 无需安装」（**零拷贝**）。

### 6.6 卸载功能：CLI 里有 ≠ 用户可用 ★★★（重要教训）

**事故**：README 写了「如何卸载：重新运行安装器 → 选择卸载 → 自动还原备份」，**但安装器 GUI 里根本没有卸载入口**（卸载逻辑 `Core.UninstallAll` 只在 CLI 里）——**用户发现后打脸**。

**修复过程**：
1. 摸清 GUI 骨架（`ui.xaml` 页脚按钮区 / `Installer.cs` 的控件接线）；
2. 页脚 Grid 扩为 4 列 + 新增 `btnUninstall`（浅灰蓝「卸载（还原备份）」，与安装操作视觉分离）；仅在组件页可见；
3. 点击 → 二次确认对话框（「将卸载本补丁已安装的内容，并还原安装前的备份文件……确定要继续吗？」）→ 执行 `UninstallAll` → 结果页逐条显示；
4. 重建 exe（+1,536 字节）→ **沙盒 GUI 实测**：
   - 首轮：btnUninstall 点击 ✓，但自动化脚本**找不到原生确认对话框**（UIA 问题，非功能问题）；
   - 视觉确认对话框正常弹出（是/否）→ 修复脚本（**UIA 全树搜索 + SendKeys ENTER 兜底**）→ 通过；
   - 结果：日志「移除补丁层 ×3 / 恢复: pack.bin ← .bak_备份 ×2 / 已还原安装前状态」——**备份还原 + 哈希删除两条路径全部实证**。

**教训（已沉淀为技能提示）**：
> **「功能存在于 CLI ≠ 用户可用」**——交付前必须按**用户视角**逐项走查每个承诺的功能入口。

### 6.7 安装器其他小坑清单

|---|---|---|
| 按钮间距不一致 | 退出按钮和下一步贴太近 | 页脚按钮对补同值 `Margin` |

## 第七部分：发布类（GitHub）

### 7.1 服务器无 gh CLI → curl REST API ★

**现象**：`gh: command not found`（发布环境没装 GitHub CLI）。

**解法**：全流程走 **curl + GitHub REST API**（建仓 / 建 Release / 上传资产 / 列资产），token 从 `~/.git-credentials` 取（注入脚本时用后即删——**凭据不进日志、不进对话**）。

### 7.2 建仓 404：组织端点 vs 用户端点 ★

**现象**：用 `/orgs/<name>/repos` 建仓 → `404 Not Found`。

**根因**：账号是**个人用户**，不是组织。

**解法**：改用 `/user/repos` 端点 → 成功。

### 7.3 100MB 单文件限制 → Release 附加下载项 ★★

**限制**：GitHub 仓库**单文件 >100MB 不能入库**（我们 3 个文件超限：EER patch00d 326MB、patch01m 252MB、DLC pack.bin 399MB）。

**用户决策**：**全部 6 个内部文件都作为同一 Release 的附加下载项**（突破仓库限制；虽然不再是"非 Release 分发"，但保证用户一次拿齐）。

**做法**：Release 资产上传（curl `uploads.github.com`，逐个文件，后台跑）；exe 作主资产 + 6 文件作附加项。

### 7.4 上传「被中断」的真相：先查再重传 ★

**事故**：本地把上传任务 kill 了，以为要重传。

**真相**：**桌面机侧的原上传其实已完整跑完**——7 个资产全部就位（只需替换后来重建的 exe）。

**教训**：**先列资产（`GET /releases/:id/assets`）核对现状，再决定重传什么**——别盲目重跑 1.1GB 上传。

### 7.5 校验时的瞬时 SSL 错误 ★

**现象**：校验 curl 报 `exit 35`（SSL connect error）。

**解法**：`--retry 4 --retry-delay 3` 重试 → 通过。**瞬时网络错误要用重试策略**，别当故障处理。

### 7.6 资源更新后的标准流水线（复用价值高）★★

```
csc 编译（含新代码）
  → 版本打桩（双语言槽注入）
  → 载荷追加（尾部附着）
  → 图标多尺寸提取 + VersionInfo 读取 + GUI 冒烟测试
  → 上传 Release（替换旧资产：先删旧 id，再传新文件）
  → 全量 SHA256 校验（7/7 资产字节级对拍）
  → 清理含 token 的临时脚本（本地 + 远程两端）
```

**实测**：新版 exe 上传 399 秒（≈2.75MB/s）；全量校验 7/7 通过后发布完成。

## 第八部分：工程环境类

### 8.1 scratch 目录被清理：密钥与脚本丢失事故 ★★★

**事故**：系统清理把 `scratch/fsnr/`（含 64KB 密钥）和 `kiminozo_dlc/`（DLC 全部管线脚本）**删掉了**——构建中断、DLC 侧脚本无法复用。

**恢复**：
- 密钥：从 GitHub 重新拉取（§1.1）；
- DLC 脚本：**没有备份，永久丢失**（只能靠档案重建——这也是本档案存在的原因之一！）。

**教训（写入项目纪律）**：
1. **一切关键资产（密钥/工具/脚本/语料）必须放项目工作区**，并定期快照；
2. **临时目录 = 一次性**，永远不要放唯一副本；
3. 文档/档案不是可选项——它是「灾难后的唯一重建依据」。

### 8.2 SSH 内联命令陷阱：`$` 和引号被吞 ★★

**现象**：`ssh host 'powershell -Command "...$var..."'` 里 `$`/引号在多层转义中被吞掉——命令行为诡异。

**解法（项目铁律）**：**远程命令一律走「脚本文件通道」**：
```
write_file（本地写 .ps1）→ scp 到远程 → ssh host 'powershell -File "X:\...\script.ps1"'
```
- 远程 PowerShell 脚本**只用 ASCII 字符**（避免编码问题）；
- 需要采集数据时，脚本内 `| ConvertTo-Json -Compress` 输出结构化结果。

### 8.3 PowerShell / C# 源文件编码规则 ★

- **远程（Windows）脚本**：ASCII-only（中文注释/字符串在多层转义下会烂）；
- **本地中文 PS1 / 含中文的 C# 源**：必须 **UTF-8 BOM**（否则 PowerShell/csc 按 ANSI 读，中文全烂）；
- XAML 等：无 BOM 也可（但要与工具链约定一致）。

### 8.4 命令通道与路径约定（双机工程）★

- 本机（WSL）跑 Python 管线；游戏机（Windows）跑装机/验收；
- 传输用 `scp`（禁止手拼 IP——用配置好的主机别名）；
- Windows 盘符路径统一正斜杠（`F:/...`）；WSL 侧 `/mnt/f/...`；
- 需要 GUI 拉起（截图/自动化测试）→ 走**计划任务**（ssh 会话没有交互桌面）。

### 8.5 `pkill -f` 自匹配自杀 ★

**现象**：`pkill -f "关键词"` 把**自己所在的 shell** 也杀了（命令行里含同样字符串 → 自匹配）。

**解法**：`pgrep` 取 PID → 按 PID kill。**别用 pkill -f 杀模糊匹配的进程**。

### 8.6 预算与止损（工程管理）★

- 长任务（复检战役）**分块**（300 条/块）跑，随时可停——**部分覆盖是合法的停止点**（我们最终以 35.4% 覆盖出货 + 全量结构扫描）；
- 用户止损指令即时生效（「token 不够了，取消后续检查」→ 未派任务全部取消）；
- 外部通道受阻（API 配额/网络）→ 切换通道（子代理接力/本地模型），**不在一棵树上吊死**。
